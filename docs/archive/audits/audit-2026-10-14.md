## 2. Detaillierte Prüfergebnisse

### Punkt 1: Regex- und Normalisierungs-Bugs in der Titelbereinigung

#### 1.1 Gemischte Trennzeichen bei Linien-Präfixen — **MITTEL**

| | |
| --- | --- |
| **Betroffene Komponente** | `src/providers/wl_lines.py:313-318` (`_WRITTEN_LIST_SEP_RE`) |
| **Problembeschreibung** | Die Regex `_WRITTEN_LIST_SEP_RE` definiert die gültigen Trennzeichen für eine manuell geschriebene Linienaufzählung im Titel. Aktuell lautet sie: `\s*[,/+]\s*|\s+und\s+|\s+(?=Rufbus\b)`. Punkte (`.`) als Trennzeichen (z. B. `4A. 80A, N29:`) fehlen. Dadurch matcht `_WRITTEN_LIST_WITH_COLON_RE` (welche diese Separatoren im Lookahead verwendet) die Aufzählung nicht als valides Linien-Präfix, weshalb der Block `4A. 80A, N29:` im Titel verbleibt und nicht entfernt wird, wodurch eine Dopplung (z.B. `4A/80A/N29: 4A. 80A, N29: Wittelsbachstraße`) entsteht. |
| **Konkreter Lösungsvorschlag** | Ergänzung des Punktes (`\.`) in der Trennzeichen-Klasse: `_WRITTEN_LIST_SEP_RE = re.compile(r"\s*[,/+\.]\s*|\s+und\s+|\s+(?=Rufbus\b)", re.IGNORECASE)` |

#### 1.2 Wortverschmelzungen beim Datums-Stripping — **MITTEL**

| | |
| --- | --- |
| **Betroffene Komponente** | `src/providers/wl_text.py:149-152` (`_AB_DATE_RE` und `_tidy_title_wl`) |
| **Problembeschreibung** | In `_tidy_title_wl` wird das Muster `_AB_DATE_RE` angewendet, das mit einem leeren String (`""`) ersetzt. Das Regex konsumiert das vorangehende Leerzeichen. Wenn der String z. B. `"Bauarbeiten ab 14.09.26"` ist, wird `" ab 14.09.26"` durch `""` ersetzt. Steht danach weiterer Text, verkleben die Wörter. Daten, die mit `"am "` beginnen (`"Veranstaltung am 14.09."`), werden gar nicht erfasst. |
| **Konkreter Lösungsvorschlag** | Die Regex sollte `"am "` aufnehmen und mit einem Leerzeichen `" "` statt mit `""` ersetzen (gefolgt von `.strip()`), um ein Verkleben sicher zu verhindern: `_AB_DATE_RE = re.compile(r"(?:^|\s+)(?:ab|am)\s+\d{1,2}\.\d{1,2}\.(?:\d{4}|\d{2})?(?!\d)", re.IGNORECASE)`. Und in `_tidy_title_wl`: `t = _AB_DATE_RE.sub(" ", t)`. |

### Punkt 2: Übersetzungs-, Masking- und Kürzungsfehler

#### 2.1 Domänen-Glossar & Fehllokalisierungen — **NIEDRIG**

| | |
| --- | --- |
| **Betroffene Komponente** | `src/build_feed.py:3551-3680` (`_GLOSSARY_BASE` und `_GLOSSARY_BY_SOURCE`) |
| **Problembeschreibung** | Das Dictionary `_GLOSSARY_BASE` deckt kulturspezifische Begriffe nicht vollständig ab (z.B. "Erntedankfest"). "Kurzführung" ist zwar für Wiener Linien gemappt, Begriffe wie "Stammstrecke" oder "Schienenersatzverkehr" fehlen (SEV wird zwar als Abkürzung maskiert, aber als ausgeschriebenes Wort nicht übersetzt). |
| **Konkreter Lösungsvorschlag** | Ergänzen fehlender Begriffe in `_GLOSSARY_BASE`: `"Erntedankfest": "Thanksgiving festival"`, `"Schienenersatzverkehr": "rail replacement service"`, `"Stammstrecke": "main route"`. |

#### 2.2 Informationsverlust durch Truncation — **MITTEL**

| | |
| --- | --- |
| **Betroffene Komponente** | `src/build_feed.py:10198-10212` (`_truncate_summary_180`) |
| **Problembeschreibung** | Die Funktion `_truncate_summary_180` bricht sehr lange Texte bei exakt 175 Zeichen am letzten Leerzeichen ab und hängt ein ` …` an. Es wird keine Rücksicht auf Satzstrukturen oder logische Blöcke (wie Kommata oder Semikolons in Aufzählungen) genommen. In `_lead_with_fragment` wird versucht, den Cut hinter einem Satzende zu platzieren, aber wenn keins gefunden wird, wird gnadenlos abgeschnitten, auch mitten in wichtigen Detailinformationen. |
| **Konkreter Lösungsvorschlag** | Smart truncation, die auch an Kommas oder Semikolons abbricht: `last_punct = max(truncated.rfind('. '), truncated.rfind('; '), truncated.rfind(', '))`. Wenn `last_punct` in der zweiten Hälfte liegt, dort abschneiden, ansonsten am letzten Leerzeichen. |

### Punkt 3: Fragile XML-/CDATA-Generierung

#### 3.1 Doppeltes Escaping (`&amp;amp;`) — **MITTEL**

| | |
| --- | --- |
| **Betroffene Komponente** | `src/build_feed.py:10236` (`_compose_description`) |
| **Problembeschreibung** | `html.escape(part, quote=False)` wird aufgerufen, um Plaintext in HTML umzuwandeln. ElementTree escaapt beim XML-Schreiben standardmäßig `&`, `<`, `>` in Text-Nodes. Da `desc_html` über CDATA injiziert wird, funktioniert das für HTML-Tags. Bei anderen Texten (z. B. plain text) führt dies jedoch zu einem doppelten Entkommen von `&` zu `&amp;amp;`, was auf Info-Displays visuell störend ist. |
| **Konkreter Lösungsvorschlag** | Für CDATA-Blöcke ist `html.escape` korrekt, für Plaintext-XML-Nodes sollte es jedoch vermieden werden, da ElementTree dies automatisch übernimmt. `desc_text_truncated` sollte nicht vorher escaped werden. |

#### 4.1 Deduplizierungslogik an Bahnhöfen — **NIEDRIG**

| | |
| --- | --- |
| **Betroffene Komponente** | `src/feed/merge.py:268-293` (`deduplicate_fuzzy`) |

Da dies aufwendiger ist, sollte es in einem eigenen PR mit umfassenden Tests geschehen. |

#### 5.1 Fehlerhafte Verklebungs-Korrektur (Regex) — **MITTEL**

| | |
| --- | --- |
| **Betroffene Komponente** | `src/utils/text.py:57` (`_GLUED_WORD_RE`) |
| **Problembeschreibung** | Die Regex `_GLUED_WORD_RE` löst Wörter, die fälschlicherweise ohne Leerzeichen gesendet wurden. ## 3. Priorisierte Roadmap für die Behebung

1. **Wortverschmelzungen / Kürzungsfehler (Punkt 1.2 & Punkt 5.1):**
   *Priorität: Sehr Hoch.* Diese Fehler verändern direkt den lesbaren Text im Feed und stören die maschinelle Übersetzung massiv. Die Anpassung der Regex-Patterns in `wl_text.py` und `utils/text.py` ist simpel und risikoarm.
2. **XML-Escaping / HTML-Darstellung (Punkt 3.1):**
   *Priorität: Hoch.* `&amp;amp;` im Output ist visuell störend auf Info-Displays. Muss in `build_feed.py` so umgebaut werden, dass Plaintext-Tags nicht durch `html.escape()` laufen.
3. **Linien-Trennzeichen (Punkt 1.1):**
   *Priorität: Hoch.* Reduziert die Wortdopplung (z.B. "4A. 80A: 4A. 80A") im Titel deutlich, was wertvollen Platz auf Bildschirmen spart.
4. **Fehlendes Domänen-Glossar (Punkt 2.1) & Truncation (Punkt 2.2):**
   *Priorität: Mittel.* Wörterbuch-Updates sind fortlaufend. Die 180-Zeichen-Truncation-Regel ist ein nettes "Quality of Life" Feature für die Lesbarkeit am Satzende.
5. **Bahnhof-Deduplizierung (Punkt 4.1):**
   *Priorität: Niedrig.* Da Provider ohnehin meist leicht unterschiedliche Informationen pro Station liefern, ist ein strengeres Deduplizieren durch IDs aufwendig und sollte in einem dedizierten PR implementiert und umfassend getestet werden.
