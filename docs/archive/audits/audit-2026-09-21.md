# Diagnostic Audit: Feed Presentation & Data Consistency

**Date:** 2026-09-21
**Mode:** STRICT AUDIT-ONLY (Read-Only)

## 1. "Bauarbeiten26" Title Anomaly
**Affected Component:** `src/providers/wl_text.py` (`_tidy_title_wl()`)
**Display Issue Description:** The date-stripping regex `_AB_DATE_RE` strips out "ab DD.MM." but strands 2-digit years because the 4-digit year component is optional `(?:\d{4})?`. For example, "Bauarbeiten ab 14.09.26" loses " ab 14.09." and leaves "Bauarbeiten" and "26", which then collapse into the malformed string "Bauarbeiten26" in the feed title.
**Proposed Solution:** Update the regex to explicitly handle 2-digit years as well as 4-digit years.
*Before:* `r"(?:^|\s+)ab\s+\d{1,2}\.\d{1,2}\.(?:\d{4})?(?!\d)"`
*After:* `r"(?:^|\s+)ab\s+\d{1,2}\.\d{1,2}\.(?:\d{4}|\d{2})?(?!\d)"`

## 2. Duplicate Title Line Prefix
**Affected Component:** `src/providers/wl_lines.py` (`_extract_prefix_lines()`)
**Display Issue Description:** Upstream Wiener Linien OGD Realtime payloads occasionally provide titles with duplicated line identifiers (e.g., "3A: 3A Netzänderung"). The parser correctly extracts the first token ("3A:") but leaves the second, bare token ("3A") in the title body because it lacks a trailing separator. When rebuilt, the title becomes "3A: 3A Netzänderung", and both instances are masked and preserved into the English translation.
**Proposed Solution:** Augment `_extract_prefix_lines()` to strip immediate residual leading line identifiers from the `body` string. Combine the canonical prefix and individual line prefixes, sort by length descending, and apply a strict regex with word boundaries `\b` to remove the redundant identifier.

## 3. Inconsistent Delay Threshold UI Label
**Affected Component:** `docs/assets/site.js`
**Display Issue Description:** The Stammstrecke UI logic uses `> DELAY_THRESHOLD_MIN` for evaluating critical delays, aligning with the backend logic (`obs.delay_minutes > DELAY_THRESHOLD_MINUTES`). However, the UI labels describe this as "≥ 9 Minuten" (greater than or equal to), creating a logical mismatch between the label and the underlying strict greater-than evaluation.
**Proposed Solution:** Update the UI text labels in `docs/assets/site.js` and `scripts/generate_markdown_stats.py` to consistently reflect the strict greater-than evaluation (e.g., using `>` instead of `≥`).
