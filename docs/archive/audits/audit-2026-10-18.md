# Audit Report 2026-10-18

## Audit Update 16:05

### Affected Component
English RSS Feed Translation (`src/feed/glossary.py`, `docs/feed.en.xml`)

### Display Issue Description
The phrase `Gleiskörper` in disruption descriptions is not translated into English, resulting in mixed-language text in the English feed output (`docs/feed.en.xml`). For example, the stop relocation of line N71 translates to `Simmeringer Hauptstraße opposite 120-122, Gleiskörper → Simmeringer Hauptstraße 157-161, temporary stop, main carriageway...`.

### Proposed Solution
Add `"Gleiskörper": "track area"` (or `"track bed"`) to `_GLOSSARY_BASE` in `src/feed/glossary.py` so the translation model picks it up.

## Audit Update 16:15

### Affected Component
Text Sanitization (`src/utils/text.py`) and OGD Baustellen Feed Output (`docs/feed.xml`, `docs/feed.en.xml`)

### Display Issue Description
OGD Baustellen payload descriptions contain awkwardly glued words that include German articles (e.g., `DieHaltestelle`, `Derrechte`, `DerFußgänger-`). The regex spacing sanitization `_GLUED_WORD_RE` in `src/utils/text.py` only handles `Im`, `Am`, `An`, `Um`, `Ab`, `In`, `Zu`, `Es`, but misses basic definite articles like `Der` and `Die`. Consequently, these glued words appear unseparated in the feed item description, leading to clumsy phrasing and potentially breaking translations.

### Proposed Solution
Modify `_GLUED_WORD_RE` in `src/utils/text.py` to include `Der` and `Die` in the list of allowed opening function words for spacing sanitization: `r"(?:(?<=[a-zäöüß]{2})|(?<=\b(?:Im|Am|An|Um|Ab|In|Zu|Es|Der|Die)))"`.

## Audit Update 16:30

### Affected Component
Feed Content Processing (`src/build_feed.py`, `src/utils/text.py`)

### Display Issue Description
The ÖBB feed items contain double-escaped HTML entities (e.g., `&amp;lt;`) within the JSON cache payload, indicating that the source data or upstream parsing step might be double-escaping XML entities like `<` and `>`. This may result in broken tags or literal entity strings in the plain text output and markdown representations if not properly sanitized or reversed before rendering. The translation model or plaintext conversion function might fail to handle these correctly.

### Proposed Solution
Review and refine `src/utils/text.py` or the specific provider (e.g., `src/providers/oebb.py`) to properly unescape double-escaped entities (e.g., `&amp;lt;` -> `<`) before converting HTML to plain text or returning the text for feed insertion. The `html.unescape` might need to be called on raw inputs or specific fields if the upstream provides double-escaped JSON strings.

## Audit Update 16:40

### Affected Component
UI Display Logic (`docs/assets/site.js`)

### Display Issue Description
The comment in `docs/assets/site.js` states: `// Kachel >= 9 unter der Beschriftung „≥ 9 Minuten", während jeder // Backend-Konsument > 9 zählte.` while the actual code renders the label as `> ${DELAY_THRESHOLD_MIN} min`. The system previously showed "≥" which incorrectly included 9, while the strict greater-than rule `>` is applied logically. There is a remnant comment and potentially translation files that still refer to "≥ 9 Minuten" while the backend counts `> 9`. The logic is technically aligned via the `> ${DELAY_THRESHOLD_MIN} min` string interpolation, so no logic bug currently exists, but UI inconsistency in translations or old comments should be noted if they affect user perception.

### Proposed Solution
This seems to have been addressed in code via `> ${DELAY_THRESHOLD_MIN} min` sub-label, but the comments still reference the old "≥" behavior. Clean up legacy comments in `site.js` to prevent future confusion about the threshold boundary.

## Audit Update 16:50

### Affected Component
Feed Summary Truncation (`src/build_feed.py` - `_truncate_summary_180`)

### Display Issue Description
The logic in `_truncate_summary_180` aggressively truncates the disruption descriptions to fit within the 180-character limit suitable for TV screens. It is known (from historical knowledge and current code logic) that this prioritization of the first sentence can cause critical multi-line disruption descriptions to drop essential re-routing information for lines mentioned in subsequent sentences.

### Proposed Solution
Modify `_truncate_summary_180` to conditionally preserve more context (e.g., specific line numbers and routing details) or adopt a smarter summarization approach that extracts and concatenates the primary disruption reason and the affected lines instead of simply cutting off blindly after 175 characters. Alternatively, provide a shorter title-focused feed alongside a full-description feed for non-TV clients.

## Audit Update 16:55

### Affected Component
Test Environment (`tests/test_update_baustellen_cache.py`, CI Pipeline)

### Display Issue Description
A test run revealed several failures related to depth bomb json parsing under Python 3.12 (e.g. `test_load_fallback_handles_json_depth_bomb`). In Python 3.12, `json.loads` handles nested arrays up to 5000 depths without raising `RecursionError` directly as in older Python versions, resulting in `update_baustellen_cache` gracefully logging "kein JSON-Objekt (got list)" instead of "ungültiges JSON" as expected by the test asserting `RecursionError`. Additionally, the CI test suite also failed due to missing `VOR_ACCESS_ID`. This is an unrelated environmental baseline test failure to this current text presentation audit and operates outside the pure visual output concern.

### Proposed Solution
For strict visual audit context, no source changes should be made to resolve this environment issue. In future updates, adjust the test suite's depth bomb assertions and the `read_capped_json` function to use deeper recursion limits or parse tests to trigger the `RecursionError` properly in Python 3.12.
