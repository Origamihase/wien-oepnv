# Audit Report 2026-10-01

## Audit Update 14:14

### Affected Component
WL Text Formatting / Output Generator (`src/providers/wl_text.py`)

### Display Issue Description
The regex pattern `_AB_DATE_RE` in `src/providers/wl_text.py` handles stripping of trailing 4-digit and 2-digit years, e.g. "ab DD.MM.[YYYY]". However, when it encounters a title with an event, such as "Veranstaltung am 04.10.2026", it doesn't do anything because it only matches "ab" (from) and not "am" (on). This leads to an inconsistent display where the date is preserved in the title as "Event on [date]" in the English feed and "Veranstaltung am [Datum]" in the German feed, making the title longer and repeating the date which is already present in the starts_at/ends_at timestamps.

### Proposed Solution
Modify the regex `_AB_DATE_RE` (or add a new similar one) in `src/providers/wl_text.py` to match both "ab" and "am" or create a dedicated replacement that targets "am [date]" formats to prevent dates from sticking to titles when they indicate single-day events (e.g. `(?:^|\s+)(?:ab|am)\s+\d{1,2}\.\d{1,2}\.(?:\d{4}|\d{2})?(?!\d)`).

## Audit Update 14:15

### Affected Component
WL Lines Parser / Prefix Extractor (`src/providers/wl_lines.py`)

### Display Issue Description
In `docs/feed.xml`, there is an entry titled "D/1/2/71/1A/3A: D, 1, 2, 71, 1A, 3A". The `_extract_prefix_lines` method in `src/providers/wl_lines.py` extracts the prefixes (D/1/2/71/1A/3A) correctly, but because the original title was likely "D, 1, 2, 71, 1A, 3A: Demonstration", the `LINES_COMPLEX_PREFIX_RE` doesn't match a trailing colon in cases where spaces or commas without a colon aren't properly captured, or more likely, it DID match, and it stripped it, but then the remaining body was just "D, 1, 2, 71, 1A, 3A" because WL sent a title that literally was just the line names or had a very strange structure. However, looking at the cache item: "title": "D, 1, 2, 71, 1A, 3A", this means there was NO colon and NO descriptive text in the title itself. Wait, if the original title from WL had no colon (e.g. it was just the line numbers), `_ensure_line_prefix` adds the "D/1/2/71/1A/3A: " prefix to the front of the original title, resulting in a duplication.

### Proposed Solution
In `src/providers/wl_lines.py` within `_ensure_line_prefix` or `_extract_prefix_lines`, improve the stripping logic to handle titles that consist ENTIRELY of comma/space separated line codes (without a trailing colon), or detect if the remaining body is purely a repetition of the extracted line codes, and if so, replace the body with a generic fallback (like "Meldung" or "Hinweis") instead of duplicating the line codes.


## Audit Update 14:16

### Affected Component
Feed XML Formatting / HTML Escaping (`src/build_feed.py`)

### Display Issue Description
The audit instruction noted: "In `src/build_feed.py`, manually escaping ampersands using `html.escape` inside XML tags can result in double-escaped entities (e.g., `&amp;amp;`) in plaintext `<description>` tags, as downstream tools like `xml.etree.ElementTree` may subsequently re-escape the already escaped text."
Checking the feed pipeline, `xml.etree.ElementTree` is indeed used. The `description` field gets doubly escaped because `xml.etree` escapes `<` to `&lt;`, `&` to `&amp;`, etc automatically when writing text nodes. If the pipeline manually escapes the `description` string before feeding it to `ElementTree`, the ampersands in `&amp;` become `&amp;amp;`. Also, in `<title>` fields, we might have issues like "D/1/2/71/1A/3A" -> if there were `&` it could become `&amp;amp;`. Looking at `docs/feed.en.xml`, `<title><![CDATA[7A/15A: Traffic congestion]]></title>`, `<title>` and `<content:encoded>` use CDATA, but `<description>` does not in some places, or perhaps it does, but if it doesn't, `xml.etree` escapes the text. Wait, `<description>` has `[01.10.2026 – 02.10.2026]`, and `&` would be escaped to `&amp;`. If `html.escape` is used in `build_feed.py` for description, it will double escape.

### Proposed Solution
Review `src/build_feed.py` and ensure that strings placed into XML text nodes via `ElementTree` are not manually escaped beforehand using `html.escape` or `cgi.escape`, unless they are being placed inside a CDATA block where ElementTree doesn't auto-escape, OR if CDATA is constructed manually. Let ElementTree handle the escaping for standard text nodes.


## Audit Update 14:17

### Affected Component
Baustellen Formatting (`src/utils/text.py`)

### Display Issue Description
The official OGD City of Vienna payload for Baustellen often provides descriptions with awkwardly concatenated sentences and compound words lacking spaces (e.g., `DerFußgängerverkehr`, `NähereInformationen`). The regex spacing sanitization in `src/utils/text.py` (`_GLUED_WORD_RE`) inserts spaces based on a strict list of allowed opening function words (e.g., `Im`, `Am`), but it misses standard German articles like `Der` and `Die`. This leaves terms like `DerFußgängerverkehr` glued together, which leads to poor presentation and potential translation issues when the English feed is generated.

### Proposed Solution
Add common German articles (`Der`, `Die`, `Das`, `Den`, `Dem`, `Des`, `Ein`, `Eine`, `Einen`, `Einem`, `Eines`, `Nähere`) to the allowed list of opening function words in the regex pattern (`_GLUED_WORD_RE`) in `src/utils/text.py`.

## Audit Update 14:18

### Affected Component
English Translation Translation Glossary / `src/build_feed.py`

### Display Issue Description
Stop relocation descriptions and other disruption announcements often contain German prefix fragments like "etwa 20 Meter in Richtung", "Ab", "Ersatzlos" that the MarianMT model may leave untranslated. Common transit nouns like "Einstieg" might be incorrectly masked as untranslatable entities (`XENT`) or not substituted via `XGLO` placeholders. Additionally, literal German transit verbs like "Busse halten" and "Züge halten" are currently not mapped to appropriate English idioms (e.g., "Buses stop at", "Trains stop"). This leads to mixed-language output or overly literal, awkward translations in the English feed (`docs/feed.en.xml`).

### Proposed Solution
Update `_GLOSSARY_BASE` in `src/build_feed.py` to properly map these terms and fragments. For example, add entries for:
- "Einstieg" -> "boarding" (using XGLO mapping to avoid entity masking)
- "etwa 20 Meter in Richtung" -> "approx. 20 metres towards"
- "Ersatzlos" -> "without replacement"
- "Ab " -> "From "
- "Busse halten" -> "Buses stop at"
- "Züge halten" -> "Trains stop"
Ensure phonetic starting sounds of English translations are considered to prevent grammar mismatches with articles generated by the MarianMT model (e.g. using "obstruction" instead of "service obstruction").
